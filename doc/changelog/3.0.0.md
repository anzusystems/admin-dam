3.0.0 — unreleased
===

Toolchain and API upgrade on top of 2.x: Vite 8, TypeScript 6, every api call on the `@anzusystems/common-admin` labs helpers, a vitest suite, a Playwright e2e suite in place of Cypress, and a long list of upload queue, list and start-up fixes. Items marked **Breaking** need action before or after deploying.

### Requirements
- **Node `^22.22.2 || ^24.15.0 || >=26.0.0`** (was `^20.19.0 || >=22.12.0`), in `e2e/` as well — `engines` was the last admin still on the old range
- **`@anzusystems/common-admin` 2.0.0** — the labs api helpers, the shared user and permission group screens, the eslint config and its `anzu/*` rules. Pinned to a beta build until 2.0.0 is released
- **common-admin's `trackNavigation` and `usePageNavigation`**, for the pages that navigate after a request
- **Local docker image `anzusystems/node:4.2.0-node24-nginx-browsers`** (from `4.1.0`); the first `bin/docker-compose build` after pulling fetches a new layer set

### Added
- **One page for the whole account, at `/users-new`.** The same person was edited in two places — `/users` for licences, licence groups, ext systems and distribution services, `/anzu-users` for roles, permission groups and grants — though they are one row and `PUT /adm/users/{id}` takes all of it; the new page saves both halves in one call. **Permission groups** from the shared common-admin screens are at `/permission-groups-new`. Both sit beside the originals, in the menu only with debug features on, until parity is confirmed; then `/users-new` takes `/users` over
- **A vitest suite** — the upload queue, list and start-up fixes below are covered by tests, and a route smoke test resolves all 69 generated routes to their own record rather than the catch-all, checks the declared and runtime name sets against each other in both directions and asserts every route has a component. Importing `vue-router/auto-routes` pulls in every page with its stores, api clients and composables, so anything that throws during module evaluation fails here; without `src/typed-router.d.ts` the suite does not load, and `yarn ci` runs `generate:dts` first. `@vitest/ui` and `yarn test:ui` as in the other admins
- **`bin/test --unit` and `--e2e`.** Without a switch it runs vitest first — no environment or browser needed, the result is on screen in seconds — then Playwright; passing both is an error, and a failing vitest run makes the script exit non-zero at the end instead of hiding behind the e2e run
- **The environment's label sits in front of the browser title** — `DEVEL: ADAM`, `STAGE: ADAM`; production sets no label, so its title is unchanged. It comes from `APP_LABEL`; a config that predates the key shows no label instead of crashing
- **The page reloads itself when a new version is deployed.** `ASystemBar` already polled `config.json` for a new `appVersion` but only lit the bar; the router guard now parks the pending navigation and reloads, a `beforeunload` veto releases the navigation after three seconds instead of leaving it hanging, and a 30-second stamp in `sessionStorage` stops a reload that does not take from looping. Same behaviour as the other five admins
- **Who created and modified a record, not only when** — every detail and edit form of the drawer pages shows the user next to the date ("Vytvorené" / "Upravené"), through `DamTrackingFields`, the common-admin rows over the dam user cache; the chip opens the user's detail
  - added where the rows were missing: the 14 edit forms, at the end of the form or in its `md=4` column where it has one (podcast, podcast episode, video show episode), the `users-new` edit and the permission group edit of `permission-groups-new`
  - an open edit form shows the time and user of the save it just made: the updates that dropped the server's answer now copy its tracking fields into the form (`syncUserAndTimeTracking`), 12 of them; the podcast and distribution category select ones already took the answer
  - the author, keyword and `users-new` details lose their own "Vytvoril" / "Upravil" rows; the TTS narration request's asset card shows its times through the same rows (the backend sends no user there)
  - the asset library, external providers, jobs, logs and the old `users`, `anzu-users` and permission group edit pages are left as they are

### Changed
- **The upload queue asks the server itself; the notification service only brings the news sooner** — until now an upload, a slot upload or an import was settled by a websocket notification, with a fallback each row armed for itself that read its asset four times and gave up after 550 s. Each queue now has one poll (common-admin's settlement of the upload queue, the same code the widgets of the other admins run), and it is always on
  - the first read comes 5 s after a file was sent, then at 10, 16, 23, 31, 40, 50 and 60 s, every 30 s to five minutes, every minute to twenty, every two minutes to an hour and every ten minutes after that, counted from the youngest waiting row, for as long as a row waits. While the notification socket is open the poll is only the backup: 10, 30 and 60 s, then every minute, every three, every five and every ten. A socket that is still connecting, or lost, does not count. Nothing is read while the tab is hidden; coming back reads once at once
  - several rows waiting in one queue are one request, `GET asset/licence/{licence}/ids/{ids}` in groups of fifty (the helper asked for 25 at a time); one row is asked about by itself, as before
  - an upload into a slot is settled without the service: its asset speaks only of its main file, so the poll reads the slots of the asset (`GET asset-slot/asset/{asset}`), which carry the file of every slot. Before, such a row stayed "processing" for good unless its file happened to be the main one
  - an import from an external provider is asked about from the answer to the import on, and a mass edit never needed the service: it loads the selection in one read and is not polled
  - a notification still settles a row at once, and its row is then no longer asked about; the read a metadata notification asks for comes 2 s after it, since the backend can send it before its transaction is committed
  - an upload whose finish request fails is asked about for as long as its row stays: the whole file is with the server by then, which may complete it, and the row then comes back as uploaded with its metadata and its form. That is for a request that got no answer (the network, a timeout) or the answer of a server in trouble (5xx). A finish request the server answered with a refusal (4xx) is final: it will not finish that file, and the row is a failed row that is not asked about
  - "processing takes too long" is said after twenty minutes instead of 550 s, and the asking goes on after it; "metadata could not be loaded" after the third read in a row that failed instead of the first, and it goes with the read that answers; a row whose asset the server does not know three times in a row fails with the unknown-error text and can be removed
  - the refresh button of a row decides by the state of the file, not of the asset: an asset that "has its file" whose file is a duplicate settled the row as processed, with a form and without the link to the original
  - the first load of a row's metadata fills only what is still empty on it — keywords, authors and each custom field by itself — so what a mass operation put into the rows while the files were still being processed stays; it used to be replaced
  - an open detail of an asset created empty gets its main file from any read of that asset, where only the metadata notification of a slot upload brought it
  - a settled row costs one read of its asset; it cost three (the state, the preview, the metadata)
  - a read that fails is written down once per outage, not once per try: the first failure of a streak goes to the api error logger (the console; Sentry where an admin sets one), the reads after it are silent until one has answered, and an asset the server does not know is written down once for its row. The poll would otherwise repeat the same failure every 15 to 300 s for as long as a row waits. The read of several rows and the read of the slots, which wrote nothing down, report their first failure the same way; the refresh button is the user asking and is written down every time. One call is kept from the logger with `execute({ report: false })` of common-admin's `useApiRequest`
  - the `uploadStatusFallback` switch is gone, see Deployment
- **Distribution statuses and the YouTube sign-in no longer depend on the notification service**
  - the distributions tab of an asset reads its list again by itself while a distribution is waiting, distributing or being processed remotely: after 15 s, 30 s, then every 30 s to five minutes and every minute after, counted from the end of the previous read; it stops when every distribution is final, when the tab is closed and while the document is hidden (one read at once on the return). Reads that keep failing come 15, 30, 60, 120 and then every 300 s apart; an answer older than a notification that arrived meanwhile is dropped
  - the YouTube dialog that waits for a sign-in asks the server again whenever the window gets the focus back or becomes visible, and loads the form once the answer is yes. It asks only whether the user is signed in, never for a new sign-in link. A refused sign-in is still learnt only from its notification
- **The upload queue runs on common-admin's upload core and draws common-admin's components** — admin-dam had its own copy of the upload service, of the queue store and of every component of the queue, beside the ones the widgets of the other admins run. It keeps what is its own: the store is common-admin's queue core with admin-dam's preset (its queues and limits, the import from an external provider, its texts), the upload service is the library's with admin-dam's requests, and the row, the list, the mass operations and the stop button of the queue are the library's components in admin-dam's wrappers. The asset image with its icons, the fail-reason chip, the keyword and author inputs with their chips, the "new author" button, the custom metadata form, the check of a picked file's format and size and the state of a drag over the window come from the library too, on the asset detail, the asset list and the author and licence pages as well. The requests are as they were but for one detail of the chunk request: the file part of a chunk carries the type of the file (for example `image/jpeg`), where admin-dam sent none and the browser put `application/octet-stream`; core-dam does not read the type of that part. The Slovak texts did not change. What a user can notice:
  - the progress of a row is measured by one meter. The ring and the percent move within a chunk as well, the bytes of the chunk on its way counted in, so a file of a single chunk no longer stands at 0 %; once the browser has taken the last chunk the row says 100 % and 0 s while the server still answers it. The speed is what was sent over the last ten seconds, the time the server takes to answer included, so the time left counts down evenly and is rather longer; a retried chunk no longer takes the percent back. On a fast network a row shows the ring with its percent and time where it often only spun. When a chunk stands still on its way, the meter reports nothing: the row keeps the speed and the time left it showed until the next byte comes, and a retry of that chunk, whose size follows the speed, is not made smaller by the silence
  - a file the server reports as failed while it is still being sent is no longer sent to its end: the chunk on the wire is aborted, no further chunk and no finish request follow, and its place goes to the next file. The row keeps the reason the server gave; a later failure of the upload itself used to put its own text over it and show an alert. The time left stays beside the red icon as it was last estimated
  - the question asked before running uploads are stopped is answered with "Zastaviť" ("Stop"); it repeated "Zatvoriť" ("Close"), the name of the button that asks, which keeps it, as does the cross of the question
  - the refresh button of a row says "Asset sa stále nahráva alebo spracováva serverom" only of a row that still waits, not of one that failed, was uploaded or stopped, or left the queue, while the server was being asked
  - the two icon buttons beside a field of the mass operations are named with their field for a screen reader — "Vyplňte prázdne pole: Kľúčové slová", "Nahradiť všade: Autori" — where every pair had the same two names; the tooltips stay short. The "+" of an author input has a name as well
  - why a keyword or an author chip shows `#id` is said in the application's tooltip, as its other tooltips are, and no longer in the title of the browser; the chip drawn as plain text keeps the title. A chip follows the name cache, so it shows the new name when the record it stands for changes there
  - an author the row has already is not offered among its author conflicts, and the heading goes with the last conflict
  - the English texts are the library's, the Slovak ones did not change: "Invalid file type" (it said "Invalid mime type"), "Original Name", "Copy asset ID", "System error. Please try again later or contact the administrator." for an upload error of no known kind, "Do you want to stop the upload?", in the mass operations "Fill empty field", "Replace everywhere", "Fill only empty", "Clear", "Main" and a longer description, and "Creating author" over the dialog of a new author
  - smaller things: the picture shown while a file uploads is an SVG of 1 kB instead of a JPEG of 58 kB of the same drawing; the list of the queue keeps a right margin of 16 px from the `md` width up; an empty chip is "-" without the spaces around it; a list of accepted types written with spaces or capitals ("image/*, .JPG") is understood; a custom metadata form pins two fields where the ext system gives no number, which the backend always does
  - who may create a keyword or an author from an input is told to the library once, with the plugin options (`keywordCreateAcl`, `authorCreateAcl` in `src/plugins/commonAdminCoreDam.ts`); the inputs of admin-dam asked the grants themselves. `App.vue` turns the watching of a drag over the window on (`initGlobalDragState()`), which the first use of the upload did
- **Actions show only to a user the backend lets do them** — they were offered to everyone and ended in a 403
  - asset library: upload (dropzone, button, empty slot) by the asset types the ext system enables, video and document with `_create` and `_update` since the backend checks their chunks under `_update`; the bulk metadata save after an upload and in mass edit; delete in the upload queue; creating an author or a keyword from the metadata form; making a file public or private; rotating an image; the ROI cropper (without `dam_regionOfInterest_update` the tab shows the image only); main file, duplicate, switch and remove in the slots; the sibling asset; the video preview image; the distribution category; a new podcast or video show episode from an asset and deleting an episode; importing from an external provider (`dam_<type>_create`)
  - a document's file is no longer offered for deletion in its slot: the backend refuses it to everyone, a super admin included
  - a new distribution, redistribution and the advanced add offer only the services on the user's account, and an advanced edit of a distribution to another service opens read-only; the integrations menu offers only the external providers on the account; deleting a distribution in the advanced settings needs `dam_distribution_delete`
  - the edit icon of podcasts, video shows and video show episodes needs `_update`, the episode's Edit button `dam_videoShowEpisode_update` instead of `dam_videoShow_update`, deleting a public export `dam_publicExport_delete` instead of `_update`
  - public exports in the menu and their list, and creating, editing, deleting and the playground of author clean phrases, are for a super admin: the backend refuses them to anyone else whatever the grants
  - the licence, licence group and ext system lists need `_list`, which their backend list checks, instead of `_read`
  - a start-up that stops because the user is not on the ext system or may not read its configuration says so, with the ext system's id, instead of the generic error page
- **Unsaved list rows ask before leaving on two pages** — the distribution category select and the podcast edit pages have the unsaved changes guard (`sources: []`, as in admin-cms): leaving with added, edited, moved or removed options or export data rows asks first; text fields do not. The asset's distributions list is `disable-unsaved` (every action is saved at once). The sortable test checks the registration
- **Vuetify's stylesheet once** — `main.scss` also `@use`d `vuetify/styles`, which `plugins/vuetify.ts` imports: the whole of Vuetify's CSS was in two startup files. Startup CSS 196 → 146 kB gzip; the production build has the same rules in the same effective order (no conflicting pair changed places)
- **Podcast, voice family and author remote autocompletes on common-admin's factory** (`props`; `scope` for the podcast's ext system, `filterFromProps` for `canBeCurrentAuthor`). `DistributionCategoryRemoteAutocomplete`, `UserRemoteAutocomplete`, `AssetLicenceByExtIdRemoteAutocomplete` and `VoiceFamilySelect` stay hand-written (a model conversion, a cloned value, a guarded fetch, a translated default label), with the fixes below
- **Every api call moved onto the common-admin labs helpers** — `useApiRequest`, `useApiFetchList`, `useApiFetchByIds`, `useApiFetchListBatch`, `useApiCommand`, `useApiFetchItems`; the `src/services/api/` functions now fail an import. The rename is mechanical and the compiler found all of it; what a response means changed in ways it does not point at:
  - a failure arrives as its own class — `AnzuApiAxiosError`, `AnzuApiTimeoutError`, `AnzuApiResponseCodeError` — instead of `AnzuFatalError` for everything, so a branch on `isAnzuApiAxiosError` can now be taken where it never was
  - a request the user superseded (another keystroke in an autocomplete, a route change mid-load) is an `AnzuApiCancelledError` and no longer raises an alert
  - a 204 answers `undefined` instead of `null`, and on a list or by-ids read `[]` — a list read used to throw `AnzuApiResponseCodeError` unless it asked for `optionalBody`, and none did. Nothing in scope answers 204 today
  - a 202 with no body resolves instead of rejecting as fatal
  - a list response is shape-checked; a malformed one is a thrown, logged error naming the url instead of `undefined` typed as an array failing somewhere unrelated later
  - `anzu/prefer-api-fetch-items` is on as an error: a `useApiRequest` typed as a list has to be `useApiFetchItems`; a call that really reads the envelope's metadata takes a per-line disable with the reason
- **User form**: creating an account asks for the same fields as editing one — it used to need only an id and an e-mail, while name, full name and avatar were required on edit alone; how strict the form is is now a property of the system. The avatar colour is validated by its shape rather than its length (`#GGGGGG` passed the form and failed on the server)
- **Sentry collects through `dataCollection` instead of the deprecated `sendDefaultPii`** (gone in SDK v11). The four categories are named one by one, even where they match today's defaults, so a default moving in v11 cannot change what is sent. `profilesSampleRate` is dropped — it never did anything without a browser profiling integration. Since `@sentry/vue` 10.75.2 `urlQueryParams` is actually applied to urls: query params whose name contains `auth`, `token`, `session`, `key`, `sid`, `identity` and similar arrive as `[Filtered]` (substring match — `keyword` too)
- **Components declare their model with `defineModel`** instead of a `modelValue` prop plus an `update:modelValue` emit; prop, emit, passthrough handler and `computed({ get, set })` collapse into one writable ref, same behaviour. A model that accepts `null` but only ever emits a real value keeps the old form, with a comment why — `defineModel` has one type for both directions

  - vue-tsc keeps its incremental build info in `node_modules/.cache/` (with vitest's test order), which the CI workflow keeps between runs (a new entry after each passing `yarn ci`, restored from the latest one for the same Node version, `yarn.lock` and tsconfigs; the `node_modules` cache leaves `node_modules/.cache` out). eslint and stylelint run without a cache and vitest without its module cache (`fsModuleCache`): eslint's and vitest's reuse a file's result without tracking the files it depends on (a cross-file rule such as `pinia/no-duplicate-store-ids`, a type imported into `defineProps`), and stylelint's hashes only the first configuration it resolves (`.vue` and `.scss` resolve differently), so a warm run could pass what a cold one reports. The old `.eslintcache` and `.stylelintcache` in the project root are no longer used and can be deleted
  - the shared eslint and stylelint config — the ones blog, forum and inhouse run — both with zero findings. `anzu/valid-route-name` is the stronger variant: the old one resolved the declaration through `process.cwd()` and checked nothing when run from a subdirectory. `@typescript-eslint/no-explicit-any` stays an error, and the two `any` casts it could not see in `<template>` blocks (`currentUser as any`, `el as any`) are typed in the script — the current user narrowed to `AnzuUserMinimal`
  - five stricter vue rules — `no-undef-components`, `attribute-hyphenation`, `v-on-event-hyphenation`, `custom-event-name-casing`, `define-emits-declaration`. The config takes Vuetify's components from its `.d.ts` and common-admin's (`Acl`, the `ABtn*` aliases) from `globalComponentNames`
  - `eslint.config.mjs` is common-admin's `defineAnzuAdminConfig({ root: import.meta.url })` and `.oxlintrc.json` extends common-admin's `oxlint-admin.json`; the admin's own copy of the config (223 lines) and its `eslint/` rule directory are gone
  - the file-based routing options live in `routerPages.config.mts`, byte for byte the same in all six admins, so vitest builds the same route table as the app
  - `.vscode/settings.json` and `extensions.json` are shared and tracked — oxfmt as formatter, fix-on-save for oxlint then eslint, stylelint over `scss` and `vue`, the workspace TypeScript; the rest of `.vscode/` stays ignored
- **The e2e suite is Playwright instead of Cypress** ([#273](https://github.com/anzusystems/admin-dam/pull/273)) — 61 specs in `e2e/`, a yarn project of its own on the shared lint and format setup (`yarn ci` = `lint:tsc`, `format:check`, `lint:oxlint`) and on TypeScript `~7.0.2`, the native compiler: there are no `.vue` files in it, and Playwright transpiles the suite itself. ### Removed

- **`dam.imageUrl`** — delivered by the config and never read since the initial commit
- **The "Nové heslo" field on the user form.** Nothing ever read it: `plainPassword` appears in no PHP in `core-dam` or `core-dam-bundle`, and the endpoint drops unknown keys. Setting a password from the admin would be a new backend feature, not a repair

As its page goes, a selection drawn over the whole page goes back to its strip, hidden (the next list empties the mass edit, as before); back on a page of the same kind (the list of another provider) the page shows its list and its strip, where it showed its own selection over the whole page, emptied. The upload queue ("Pridať popis") is the same on both lists and is drawn over the next one whole, as before. "Uložiť a ukončiť" of the mass edit whose answer comes after its page was left no longer empties the mass edit and puts it away on the page the user is on by then: the next list emptied it as it was drawn, and what it holds by then was picked there - the tiles picked on the list of a provider, its strip and a selection opened over the whole page stay. A way out that is still asking ("Neuložené zmeny" of the panel beside the list) or was called off ("Zostať") has not left the page: the mass edit is emptied and put away there, as on any answer on its page. "Uložiť a ukončiť" of the upload queue whose answer comes after the queue was put away into its strip no longer closes a selection drawn over the whole page since (the dialog went, the selection still set to be drawn over the whole page) nor turns the arrow keys of the list on under it; the queue is stopped and hidden as before. The saves and "Záznam bol upravený." are as before

### Deployment
- **`config.json.dist` no longer asks for `API_LOG_ERROR_ENABLED`, `API_LOG_ERROR_URL` and `DAM_IMAGE_URL`, and asks for `APP_LABEL`.** A deployment that supplies its own template — the petit deploy repository keeps a `config.json.cf.dist`, which already carries `appLabel` — can drop the `apiLogError` and `dam.imageUrl` keys and those variables once no version still reading them is a rollback target. Until then leave them: `apiLogError.enabled` sits in an unquoted position, so an unresolved token there is invalid json
- **`config.json.dist` no longer asks for `UPLOAD_STATUS_FALLBACK`, and `uploadStatusFallback` is no longer read.** The upload queue always asks the server itself, so there is nothing to switch; `.env` lost the variable too. A deployment that supplies its own template can drop the key and the variable at any time: a config that still carries it starts as before, the key is read past
- **The `notification` block of `config.json` is optional, and the service is on only when a deployment says so**: `enabled` is `true`, or the text `true` in whatever case and with spaces around it (`"true"`, `"True"`, `" TRUE "`), with a non-empty `webSocketUrl`. A config without the block starts with the service off — it used to stop the start with the fatal error — and so does a block that leaves one of its two values out. **Check before deploying:** any other value is off now — `"1"`, `"yes"`, an empty text — and so is the text `"false"`, which used to count as on (a template that puts the value in quotes). An environment that had its notifications on that way has them off from this version: uploads, slot uploads, imports, distribution statuses and the YouTube sign-in then go by polling alone, a few seconds later than with the socket
- **`APP_LABEL` has to be defined in every environment, production included, where it is empty.** `replacetokens` leaves an unknown `#{APP_LABEL}#` in place rather than blanking it, so a missing variable would print the token into the title
