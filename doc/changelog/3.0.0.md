3.0.0 — unreleased
===

> **TODO before the release:** if admin-dam does not release 2.3.0 from develop first, merge develop and record here what it brings: #271 (uploadedAt filter, rejection reason in the upload queue, licence flags and autoDelete) and #273 (the Playwright e2e suite in place of Cypress).

Toolchain and API upgrade on top of 2.x: Vite 8, TypeScript 6, the API calls on the `@anzusystems/common-admin` 2.0 helpers, a vitest suite and a long list of upload queue, list and start-up fixes. What a deployment has to check is under Deployment.

### Requirements
- **Node `^22.22.2 || ^24.15.0 || >=26.0.0`** (was `^20.19.0 || >=22.12.0`), in `e2e/` as well — `engines` was the last admin still on the old range
- **`@anzusystems/common-admin` 2.0.0** — the common-admin 2.0 API helpers, moved from `/labs` to the main package entry, the shared user and permission group screens, the eslint config and its `anzu/*` rules. Pinned to the prerelease 2.0.0-rc.5 until 2.0.0 is released
- **Local and CI docker image `anzusystems/node:4.2.0-node24-nginx-browsers`** (from `4.1.0`); the first `bin/docker-compose build` after pulling fetches a new layer set

### Added
- **One page for the whole account, at `/users-new`** — licences, licence groups, ext systems and distribution services (until now `/users`) and roles, permission groups and grants (until now `/anzu-users`) are edited together and saved in one `PUT /adm/users/{id}`. **Permission groups** from the shared common-admin screens are at `/permission-groups-new`. Both sit beside the originals, in the menu only with debug features on, until parity is confirmed; then `/users-new` takes `/users` over
- **A vitest suite** — the upload queue, list and start-up fixes below are covered by tests, and a route smoke test resolves all 75 generated routes, so a page that throws while its modules load fails the suite. Without `src/typed-router.d.ts` the suite does not load; `yarn ci` runs `generate:dts` first. `@vitest/ui` and `yarn test:ui` as in the other admins
- **`bin/test --unit` and `--e2e`** — without a switch it runs vitest first, then Playwright; passing both is an error, and a failing vitest run makes the script exit non-zero at the end
- **The environment's label sits in front of the browser title** — `DEVEL: ADAM`, `STAGE: ADAM`; production sets no label, so its title is unchanged. It comes from `APP_LABEL`; a config without the key shows no label
- **The page reloads itself when a new version is deployed** — the router guard holds the navigation and reloads once `ASystemBar` sees a new `appVersion`; a `beforeunload` veto releases the navigation after three seconds, and a reload that does not take is not repeated for 30 s. Same behaviour as the other five admins
- **Who created and modified a record, not only when** — the details and edit forms of the drawer pages show the user next to the date ("Vytvorené" / "Upravené"); the chip opens the user's detail
  - added to the 14 edit forms, the `users-new` edit and the permission group edit of `permission-groups-new`
  - an open edit form shows the time and user of the save it just made (12 updates copy the server's tracking fields into the form)
  - the author, keyword and `users-new` details lose their own "Vytvoril" / "Upravil" rows; the TTS narration request's asset card shows its times through the same rows
  - the asset library, external providers, jobs, logs and the old `users`, `anzu-users` and permission group edit pages are left as they are

### Changed
- **The upload queue asks the server itself; the notification service only brings the news sooner** — an upload, a slot upload or an import was settled by a websocket notification, with a fallback per row that gave up after 550 s. Each queue now has one poll (common-admin's, the same the widgets of the other admins run), always on
  - the first read comes 5 s after a file was sent, then less and less often (every ten minutes after an hour) for as long as a row waits; with the socket open the poll is only the backup (10, 30, 60 s, then every minute up to every ten); nothing is read while the tab is hidden, and coming back reads once
  - several waiting rows are one request, `GET asset/licence/{licence}/ids/{ids}` in groups of fifty; a slot upload is settled from the slots of its asset (`GET asset-slot/asset/{asset}`) and no longer stays "processing" for good when its file is not the main one; an import is asked about from the answer to the import on; a mass edit is not polled
  - a notification still settles a row at once; the read a metadata notification asks for comes 2 s after it, since the backend can send it before its transaction is committed
  - an upload whose finish request got no answer or a 5xx is asked about for as long as its row stays, and comes back as uploaded with its metadata if the server completes it; a 4xx is final and the row fails
  - "processing takes too long" is said after twenty minutes instead of 550 s and the asking goes on; "metadata could not be loaded" after the third failed read in a row; an asset the server does not know three times in a row fails the row with "Súbor už na serveri nie je." (an uploaded row waiting for its form: "Asset už neexistuje."), and refresh is offered 20 s after the row turned uploaded
  - the refresh button decides by the state of the file, so a duplicate is no longer settled as processed without the link to its original
  - the first load of a row's metadata fills only what is still empty, so what a mass operation put into the rows meanwhile stays
  - an open detail of an asset created empty gets its main file from any read of that asset
  - a settled row costs one read of its asset instead of three
  - a failing read is written to the api error logger once per outage, not on every try; the refresh button is written down every time
  - the `uploadStatusFallback` switch is gone, see Deployment
- **Distribution statuses and the YouTube sign-in no longer depend on the notification service**
  - the distributions tab reads its list again while a distribution is waiting, distributing or being processed remotely (after 15 s, 30 s, then every 30 s to five minutes and every minute after), stops when all are final, when the tab closes and while the document is hidden, and backs off when reads keep failing; an answer older than a notification that arrived meanwhile is dropped
  - the YouTube dialog that waits for a sign-in asks the server again when the window gets the focus back or becomes visible, and loads the form once the user is signed in; a refused sign-in is still learnt only from its notification
- **The upload queue runs on common-admin's upload core and draws common-admin's components** — the queue store, the upload service, the row, list, mass operations and stop button, the asset image, the fail-reason chip, the keyword and author inputs, the "new author" button, the custom metadata form, the format and size check of a picked file and the drag state of the window are the library's, with admin-dam's preset (queues, limits, the external-provider import, texts). The requests are the same, except that the file part of a chunk carries the file's type (core-dam does not read it). The Slovak texts did not change. What a user can notice:
  - the progress ring and percent move within a chunk too, so a single-chunk file no longer stands at 0 %; the speed is that of the last ten seconds, so the time left counts down evenly; a retried chunk no longer takes the percent back, and a stalled chunk keeps the last speed and time left
  - a file the server reports as failed while it is still being sent is aborted, its place goes to the next file, and the row keeps the server's reason instead of a later text and alert
  - the question before running uploads are stopped is answered with "Zastaviť" ("Stop") instead of "Zatvoriť" ("Close"); Esc closes it and stops nothing
  - the refresh button says "Asset sa stále nahráva alebo spracováva serverom" only of a row that still waits
  - the icon buttons of the queue have names for a screen reader: refresh and cancel of a row and the stop button by their tooltip, the two buttons beside a field of the mass operations with the field ("Vyplňte prázdne pole: Kľúčové slová"); the "+" of an author input has one too
  - why a keyword or author chip shows `#id` is said in the application's tooltip instead of the browser's title (plain-text chips keep the title), and a chip shows a record's new name when it changes in the cache
  - an author the row already has is not offered among its author conflicts
  - the English texts are the library's ("Invalid file type", "Original Name", "Copy asset ID", "Do you want to stop the upload?", "Fill empty field", "Replace everywhere", "Creating author", …)
  - smaller things: the uploading picture is a 1 kB SVG instead of a 58 kB JPEG; the queue list keeps a 16 px right margin from `md` up; an empty chip is "-"; accepted types written with spaces or capitals ("image/*, .JPG") are understood
  - who may create a keyword or an author from an input is configured once in the plugin options (`keywordCreateAcl`, `authorCreateAcl` in `src/plugins/commonAdminCoreDam.ts`); `App.vue` turns on the watching of a drag over the window (`initGlobalDragState()`)
- **Actions show only to a user the backend lets do them** — they were offered to everyone and ended in a 403
  - asset library: upload (dropzone, button, empty slot) by the asset types the ext system enables, video and document with `_create` and `_update` since the backend checks their chunks under `_update`; the bulk metadata save after an upload and in mass edit; delete in the upload queue; creating an author or a keyword from the metadata form; making a file public or private; rotating an image; the ROI cropper (without `dam_regionOfInterest_update` the tab shows the image only); main file, duplicate, switch and remove in the slots; the sibling asset; the video preview image; the distribution category; a new podcast or video show episode from an asset and deleting an episode; importing from an external provider (`dam_<type>_create`)
  - a document's file is no longer offered for deletion in its slot: the backend refuses it to everyone, a super admin included
  - a new distribution, redistribution and the advanced add offer only the services on the user's account, and an advanced edit of a distribution to another service opens read-only; the integrations menu offers only the external providers on the account; deleting a distribution in the advanced settings needs `dam_distribution_delete`
  - the edit icon of podcasts, video shows and video show episodes needs `_update`, the episode's Edit button `dam_videoShowEpisode_update` instead of `dam_videoShow_update`, deleting a public export `dam_publicExport_delete` instead of `_update`
  - public exports, and creating, editing, deleting and the playground of author clean phrases, are for a super admin: the backend refuses them to anyone else
  - the licence, licence group and ext system lists need `_list`, which their backend list checks, instead of `_read`
  - a start-up that stops because the user is not on the ext system or may not read its configuration says so, with the ext system's id, instead of the generic error page
- **The logs are common-admin's log view at `/logs/dam/:type[/:id]`, for a super admin, and bookmarks of the older paths open the log** — `/log/:system/:type/:id` (before 2.0.0), `/logs/:system/:type/:id` (2.x) and `/logs` redirect there, without the rest of the path. The system is in the address instead of a filter select. The menu item and the pages need a super admin of DAM, which the backend checks, instead of `dam_log_ui`
- **"Zatvoriť" goes back to where the user came from** — the close button of every detail and edit page goes back to the previous page of the application (a list, or another record that linked to it), never to another view of the same record, a record under it, the create form or a page that only redirects; with nothing to go back to it goes where it went before. Two details that link to each other, or a DAM user's detail and its "Úprava oprávnení", are not closed back and forth
- **Unsaved list rows ask before leaving the distribution category select and podcast edit pages** — added, edited, moved or removed options or export data rows; text fields do not. The asset's distributions list saves every action at once and asks nothing
- **User form of `/users-new`** (common-admin's): creating an account asks for the same fields as editing one — the old `anzu-users` form needs only an id and an e-mail, while name, full name and avatar are required on edit alone. The avatar colour is validated by its shape (`#GGGGGG` passes the old form and fails on the server)
- **The English title of the ext system and licence dialog says "Media Library"** — "Switch Media Library ext system and asset licence", where it said "DAM"
- **The API calls use the common-admin 2.0 helpers from the main package entry; the old `/labs` entry is gone** — `useApiRequest`, `useApiFetchList`, `useApiFetchByIds`, `useApiFetchListBatch`, `useApiCommand`, `useApiFetchItems`. What a response means changed:
  - a failure arrives as its own class (`AnzuApiAxiosError`, `AnzuApiTimeoutError`, `AnzuApiResponseCodeError`) instead of `AnzuFatalError` for everything
  - a request the user superseded (another keystroke in an autocomplete, a route change mid-load) is an `AnzuApiCancelledError` and raises no alert
  - a 204 answers `undefined` instead of `null`, and `[]` on a list or by-ids read, which used to throw; a 202 with no body resolves instead of rejecting as fatal
  - a list response is shape-checked; a malformed one is a logged error naming the url
  - `anzu/prefer-api-fetch-items` is an error: a `useApiRequest` typed as a list has to be `useApiFetchItems`
- **Sentry**
  - collects through `dataCollection` instead of the deprecated `sendDefaultPii` (gone in SDK v11), the four categories named one by one so a moved default cannot change what is sent; `profilesSampleRate`, which never did anything here, is dropped. Since `@sentry/vue` 10.75.2 `urlQueryParams` is applied: query params whose name contains `auth`, `token`, `session`, `key`, `sid`, `identity` and similar arrive as `[Filtered]` (substring match — `keyword` too)
  - `extraErrorDataIntegration({ depth: 3, captureErrorCause: false })` as in admin-cms: the properties of common-admin's error classes reach the event, the cause only by its message
  - the build uses `anzuSentry({ project: 'anzu-admin-dam' })` from `@anzusystems/common-admin/vite`, as all six admins: frames from common-admin resolve to its sources, maps stay `hidden` and are deleted after the upload, and a missing `SENTRY_AUTH_TOKEN` or a failed upload fails the build instead of a warning

  - the podcast, voice family, author and video show remote autocompletes and the ext system filter are `createRemoteAutocomplete` / `createFilterRemoteAutocomplete` calls under the same file names; `DistributionCategoryRemoteAutocomplete`, `UserRemoteAutocomplete`, `AssetLicenceByExtIdRemoteAutocomplete` and `VoiceFamilySelect` stay hand-written
  - `index.html` puts common-admin's `anzu-common` layer between `vuetify-overrides` and `vuetify-utilities` and fixes the order of Vuetify's sub-layers, which otherwise depended on which stylesheet loaded first
  - common-admin loads per page: one file per module, the single `common-admin` chunk is gone, a `$initial` chunk group holds what the app needs at startup
  - Vuetify's stylesheet is in the startup files once (startup CSS 196 → 146 kB gzip), with the same rules in the same effective order
- **Code**
  - components declare their model with `defineModel` instead of a `modelValue` prop and an `update:modelValue` emit, same behaviour
  - every module imports what it uses and unplugin-auto-import is gone (codemod `scripts/codemods/explicit-imports` of common-admin, manifest in `scripts/explicit-imports.manifest.json`); `generate:dts` deletes the `src/auto-imports.d.ts` and `.eslintrc-auto-import.json` a clone still has and fails if they come back. Dev and the tests now validate imported prop types (31 components)
  - imports are sorted and checked: oxfmt sorts the statements (`sortImports`, side-effect imports keep their place, comments in `main.ts` keep the stylesheet order), oxlint the names, duplicates and `import type` (`sort-imports`, `import/no-duplicates`, `import/consistent-type-specifier-style`); the one-time reordering is a commit of its own

### Removed
- **Our own error logging** — `ErrorHandlerApiService`, `createLog` and the `apiLogError` config; Sentry runs everywhere
- **`dam.imageUrl`** — delivered by the config and never read
- **The "Nové heslo" field, on the user page at `/users-new`** — nothing ever read `plainPassword` in `core-dam` or `core-dam-bundle`, and the endpoint drops unknown keys. The old `/users` edit still shows it until `/users-new` takes `/users` over
- **The browserslist update of `yarn production` and `yarn development`, and `.browserslistrc`** — both builds ran `browserslist --update-db`, which rewrites `yarn.lock` in the middle of a build; nothing read `.browserslistrc` (the query is in `vite.config.mts`). `browserslist:update` stays as a manual script, on `update-browserslist-db` now

### Fixed
- **Navigation, start-up and sign-in**
  - a navigation that fails (page code that did not download, a guard that threw) shows "Stránku sa nepodarilo otvoriť."; a page whose code is gone after a deploy says the same and does not reload the tab, which would take a running upload queue with it
  - a redirect after a create, a save or a delete no longer cancels a navigation the user started meanwhile, nor pulls the user back from the page they went to; a record page whose load fails meanwhile leaves no message there, and the asset list's quick detail no longer rewrites the address after the user has left
  - a start-up failure that says nothing about the user leads to a new error page with a retry instead of the sign-in screen, and reloading that page retries too; an asset link the server answers with 404 or 403 leads to not-found; a sign-in the SSO already refused is answered before the start-up fetches anything. An outage of the current-user endpoint alone still looks like a sign-in problem
  - an error while the app starts is reported as itself (Sentry once it runs), not as a config that did not load; a failing public configuration no longer leaves a blank page
  - the sign-in button shows it is working and a second submit starts no second request; a successful sign-in reloads the page, so signing in as somebody else no longer keeps the previous user's permissions and configuration
  - signing in leaves no `/login` entry in the browser history, the SSO button behaves as a link with Ctrl, Cmd, Shift, Alt or the middle button, and the sign-out takes the place of its `/logout` entry, so Back after a new sign-in does not sign the user out again
  - `/`, where the logo leads, replaces itself with the asset list in the history, so Back from the list goes to the page before it
  - a detail or edit page whose record does not load says why ("Záznam neexistuje alebo bol vymazaný." on a 404, "Na tento záznam nemáte oprávnenie." on a 403, the usual message otherwise) and goes back to the view the user came from, else to the list, instead of showing the form's defaults with Edit, Save and Delete live; a load still running when the page is left shows nothing. Every drawer page with a record, `users-new`, `permission-groups-new`, the old `anzu-users` and permission group pages and the log detail included
  - the router opens the 404 page for an id that cannot exist: an author, keyword, podcast, video show, episode, distribution category, distribution category select, voice family or TTS narration request id that is not a UUID, an author clean phrase or job id that is not a number (`12abc` opened and saved record 12), a log id that is not 24 hex characters
  - a podcast's and a video show's episode list and a voice family's voices wait for their record instead of fetching after a failed load; a user whose licence groups do not load and a distribution category whose selects do not load stay on the detail without them, while the distribution category edit goes back, since its Save would clear the selected options
  - Save on the user and permission group edit pages shows only once the record is loaded
  - an episode opened under another podcast or video show puts its own one into the address, so the breadcrumb and the way back are right
  - the breadcrumb of a DAM user's detail and edit reads "Používateľ #42" instead of the bare id after a "0"
  - the page of an asset or of a file left right after it opened reads nothing, so the next page no longer shows "Nesprávne ID assetu alebo neoprávnený prístup"
- **Client and auth**
  - `damClient()` no longer registers another pair of interceptors on the shared instance with every request and chunk; its `timeoutBase` and `onUploadProgress` arguments never worked, and chunk uploads pass their longer timeout in the request config
  - requests waiting for a token refresh are released in the right order, so none is left in a queue nobody flushes
  - a token refresh the server refuses logs the user out once instead of twice
  - notification listeners are registered once instead of once per start-up, and reading the auth cookies no longer leaks a VueUse `useCookies()` instance per call
- **Upload queue** ([#86567](https://dev.azure.com/petitpress/Anzu/_workitems/edit/86567))
  - cancelling stops an upload wherever it stands (between chunks, while a chunk is read, during a retry back-off); the asset it already created stays on the server
  - removing an item while it uploads stops it like cancelling, without a failure the user caused, and refills the freed slot at once
  - the queue keeps to two parallel uploads, and a failed external-provider import no longer holds a slot for the rest of the session
  - two uploads into different slots of one asset no longer settle each other, a second upload into the same slot shows its progress, and two files of one name no longer share a key
  - a retried chunk no longer reports a negative speed that shrank the chunk size to its minimum
  - dropping a folder offers all its files, not the first hundred, and an entry that is neither file nor folder no longer leaves the drop waiting
  - the size limit accepts a file exactly at the limit, as the backend does, and the `*` and `.extension` forms of the limit map are applied the right way round
  - a stopped, removed or cleared row is no longer asked about; a row that waits long says why and can be cancelled; one failed read no longer ends the asking; a slot is no longer reported finished by the asset's main file
  - an upload whose metadata cannot be read says so, offers refresh after twenty seconds at the latest, and refresh loads the missing metadata; the bulk save no longer skips such a row in silence
  - an upload no notification comes for is settled as a notification would settle it: a processed one gets its metadata and form, a duplicate the link to its original
  - a row's metadata is loaded once (by its notification, the poll or refresh, whichever answers first), so a later answer no longer replaces what the user typed, and the single-use switch of such a row is no longer reset
  - a duplicate and a failed row stay not editable and keep their reason whatever order the notifications come in; a failed row whose file the server processed after all becomes an uploaded row again, with the form as the user left it
  - a file notification no longer fails an asset picked for mass edit before it had a file
  - refresh says when it could not find out ("Stav položky sa nepodarilo načítať. Skúste to znova.", "Asset už neexistuje.") and asks about the row it was pressed on, also when the list moved under the press
  - the limit dialog adds files to a slot as files of that slot, not as new assets
  - clearing a queue stops the uploads it holds, as stopping the queue does (today only the mass-edit selection is cleared so, and nothing changes on screen)
  - an upload whose start the server answers without a file or asset id fails at once with one alert, instead of sending its chunks to `…/undefined/chunk`; an import answered that way fails at once too
  - an upload whose file the server no longer has says "Súbor už na serveri nie je." instead of the general error, and the next unexplained failure gets its alert again

### Deployment
- **`config.json.dist` no longer asks for `API_LOG_ERROR_ENABLED`, `API_LOG_ERROR_URL` and `DAM_IMAGE_URL`, and asks for `APP_LABEL`.** A deployment that supplies its own template — the petit deploy repository keeps a `config.json.cf.dist`, which already carries `appLabel` — can drop the `apiLogError` and `dam.imageUrl` keys and those variables once no version still reading them is a rollback target. Until then leave them: `apiLogError.enabled` sits in an unquoted position, so an unresolved token there is invalid json
- **`config.json.dist` no longer asks for `UPLOAD_STATUS_FALLBACK`, and `uploadStatusFallback` is no longer read.** The upload queue always asks the server itself, so there is nothing to switch; `.env` lost the variable too. A deployment that supplies its own template can drop the key and the variable at any time: a config that still carries it starts as before, the key is read past
- **`config.json.dist` has no Sentry DSN.** The DSN stays the secret `admin-dam-sentry-dsn` of the deploy repository's `config.json.cf.dist`; an app started from `config.json.dist` runs without Sentry, and `SENTRY_DSN` is gone from `.env`
- **The `notification` block of `config.json` is optional, and the service is on only when a deployment says so**: `enabled` is `true`, or the text `true` in whatever case and with spaces around it (`"true"`, `"True"`, `" TRUE "`), with a non-empty `webSocketUrl`. A config without the block starts with the service off — it used to stop the start with the fatal error — and so does a block that leaves one of its two values out. **Check before deploying:** any other value is off now — `"1"`, `"yes"`, an empty text — and so is the text `"false"`, which used to count as on (a template that puts the value in quotes). The petit deploy template quotes it and its three variable groups set `true`, so the service stays on there. An environment that had its notifications on that way has them off from this version: uploads, slot uploads, imports, distribution statuses and the YouTube sign-in then go by polling alone, a few seconds later than with the socket
- **`APP_LABEL` has to be defined in every environment, production included, where it is empty.** `replacetokens` leaves an unknown `#{APP_LABEL}#` in place rather than blanking it, so a missing variable would print the token into the title
- **Review log access before deploying.** `dam_log_ui` no longer grants access to the logs: every user who still needs them has to be a super admin of DAM (the logs entry under Changed)
