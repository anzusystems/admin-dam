planned
===

### Fixed

- **Cancelling an upload now stops it where it stands.** The cancel token reached only a request
  that was on the wire, so a stop asked for between two chunks, or while the next one was being read
  off disk, was ignored and the file went on uploading — a stop during a retry back-off was caught
  only later, by the cancelled token failing the next attempt and the retries running out. The chunk
  loop now checks at every point it can be interrupted, and the first and last request of an upload
  are checked on the side each of them can be: after the one that opens the upload, before the one
  that finishes it. Neither request is cancelled itself, so a stop during the opening one takes
  effect only once it answers, and one during the finishing request not at all. Either way the asset
  the upload had already created stays on the server; only the queue item goes.
- **Removing an item from the queue while it uploads no longer reports a failure that did not
  happen.** The asset is deleted server-side first, so the loop went on posting chunks to something
  that was gone and ended on an error message about an upload the user had cancelled. The removal
  now tears the upload down the same way stopping it does, and refills the slot it freed at once —
  until now the queue waited for the orphaned upload to exhaust its retries first.
- **A request waiting for a token refresh is released in the right order.** The “a refresh is in
  flight” flag came down in a `.finally`, which runs after the continuations of the requests that
  flush had just released: one of those making a request of its own inside that window would find
  the flag still up and join a queue nobody was going to flush again. The flag now comes down before
  the flush, and the queue is detached before it is walked rather than emptied by a `filter` over
  the callbacks themselves.
- **The upload queue keeps to its two parallel uploads.** It started two more whenever a slot came
  free, without counting the ones already running, so the number crept up under a long queue.
- **A stopped or cleared upload no longer leaves its notification fallback timer behind.** The timer
  reschedules itself, so an item removed while it waited went on polling for the asset for minutes.
  A chain that had already started now stops on any settled item, rather than only on a finished one — and it asks again after its own request comes back, so a queue
  cleared while that request was out does not have the next attempt scheduled on top of it.
- **Reporting an error no longer signs the user out.** The log request went through the
  authenticated client, whose request interceptor signs the user out when there is no auth cookie
  and whose response interceptor does the same on a 401 — reporting an error is exactly the moment
  neither should happen, and the log endpoint being an absolute url puts it past the prefix filter
  that keeps the auth and configuration endpoints out. The log now goes through a client of its own,
  and a rejected log request is no longer an unhandled rejection.
- **The client no longer collects an interceptor per request.** `damClient()` is a factory called on
  every request — chunked uploads call it once per chunk — and it registered its request and
  response interceptors on the shared instance each time, so the handler arrays grew without bound
  for as long as the tab was open. The two arguments it accepted, `timeoutBase` and
  `onUploadProgress`, reached the instance only on the very first call — the one that created it,
  which is never a chunk upload — so for what they were for they never worked; chunk uploads now
  pass their
  longer timeout in the request config.
- **Notification listeners are registered once.** A repeated start-up added another listener and
  opened another connection, and nothing tore either down.
- **Reading the auth cookies no longer leaves a listener behind.** Both readers run outside a Vue
  effect scope, where VueUse's `useCookies()` leaks a `Cookies` instance and a permanent change
  listener per call and its own cleanup is a silent no-op.
- **A bulk metadata save no longer writes flags nobody edited.** The payload always carried
  `mainFileInternal`, `mainFileOverrideInternal` and `ttsAudio` as `false`, and the queue never
  learned their real values, so changing one keyword on a TTS asset turned that off, and the
  internal flags were re-decided from a `false` the user had never chosen — the backend re-runs its
  internal rules on every save, so what came out of that depended on them. It now sends only what
  the form edits; a field the payload leaves out is one the save does not write, though those rules
  still run and can move the internal flags on their own.
- **A failed import from an external provider no longer stops the queue.** Every failure but a
  duplicate resolved with the item still uploading, which holds one of the two parallel slots for
  the rest of the session — two of them and nothing else started.
- **Two uploads into different slots of one asset no longer settle each other.** The notification
  names the file, but only the asset was read from it, so the first result marked the second one
  finished or failed.
- **A second upload into the same slot shows its progress again.** Finished items stay in the slot
  queue until it is cleared by hand, and the lookup answered with the first match — the previous
  upload — so the new one had no progress bar and the slot never refreshed when it finished.
- **Dropping a folder offers all of it.** The directory reader was asked once, and browsers answer
  in batches — Chromium in hundreds — so a folder of three hundred files quietly became the first
  hundred, and the rest were never mentioned. The upload dialog's own limit on how many files it
  takes at a time still applies to what comes out. An entry that is neither a file nor a folder no
  longer leaves the drop waiting for ever.
- **A notification that never arrives no longer leaves an item without an explanation.** The
  fallback gave up after its last attempt in silence, and a single failed request ended the retry
  chain for good. It now says what happened and keeps trying after a transient failure, and it no
  longer reads the asset's main file when that is not the file the item uploaded — which used to
  report a slot as finished on the strength of a different file entirely. A slot upload therefore
  usually needs its notification: unless the backend has made that file the asset's main one — which
  it does when there was none — the fallback cannot read it, so it can only say that it has given up
  waiting, not finish the item. Such a row can now at least be cancelled, and the reason it gives up
  is on the warning icon; the row itself is too small to print it.
- **A retried chunk no longer reports a negative speed.** The progress baseline survived the failed
  request, so the first sample of the retry was a large negative number — which dragged the average
  down and collapsed the adaptive chunk size to its minimum just as the connection was worst.
- **A start-up that fails no longer looks like a sign-in problem.** Anything that was not about the
  user's identity ended on the sign-in screen, including a link to an asset that had been deleted.
  Failures that carry no verdict about the user now lead to a new error page with a retry, and a
  link to an asset the server answers 404 or 403 for leads to the not-found page — anything else it
  cannot answer goes to that error page rather than claiming the asset is missing. The page says
  only that the start-up did not finish, and offers to try again: the configuration endpoints behind
  it are permission-checked too, and the library answers their failures with a bare `false` that
  says nothing about which it was. A sign-in the SSO has already refused is answered before the start-up
  fetches anything of its own, and it now waits for both of its requests rather than giving up on the
  first failure — the current-user answer is the only thing that tells a stale session from a
  broken server, and `loadDamPrvConfig` rejects with a bare `false` that carries no status of its
  own. One case is beyond reach here: the current-user request answers `undefined` for every
  failure alike, so a backend outage on that one endpoint still looks like a sign-in problem.
- **A failing public configuration no longer leaves a blank page.** It was awaited in the router
  guard with nothing to catch it, so the first navigation was aborted.
- **A list page that fails to load is retried rather than skipped.** The page counter was raised
  before the request and never put back, so the next scroll asked for the one after it. A list
  started again from page one — by a filter change, say — also discards the rows the requests it
  replaced bring back, in both lists: the older answer of two filter changes used to be the list
  the user was left looking at. Scrolls are served one at a time as well, in both lists: two of them
  running at once append in whatever order they answer, and one that fails while the other has moved
  the counter past it is gone for good. A scroll that
  arrives while one is running is remembered and served afterwards, unless the list it was asked of
  has been replaced since, could not load, or the answer that arrived meanwhile says there is no
  next page. A request left over from a list that has been replaced does not stand in the way of the
  new one's scroll: nothing aborts it, so waiting for it would mean waiting out its whole timeout.
  Each request is handed a pagination object of its own, because the library replaces the value of the
  one it is given before it returns — an answer that no longer owns the list used to tell the new
  one there was nothing more to load, and the scroll stopped there.
- **A tile stays highlighted only while its asset is in the mass edit queue**, in both lists. The
  highlight and the queue were kept in step by hand, so every action that added an asset set the flag
  itself — and the ones that take it back out again cannot reach the list at all: the cancel and
  delete buttons in the mass edit dialog, the bin in the external provider's selection dialog, and
  the import, which empties the whole queue. The tile stayed highlighted for an asset nothing was
  going to save, and it took two clicks to select such an asset again. The highlight now follows the
  queue.
- **A file notification no longer fails an asset picked for mass edit before it had one.** Such a row
  carries no file id, so nothing in the event tells it apart from a slot upload into the same asset —
  the notification does not say whether its file is the asset's main one. Only the handler a wrong
  guess costs nothing still acts on such a row: the processed one, and it only brings the asset
  status and the preview — the status of a row picked for mass edit belongs to the batch load that
  put it there, no notification settles it, and the single-use switch is left as the user set it
  rather than overwritten with the server's copy. A failure or a duplicate would put a terminal state
  on a row that is doing fine, so those two leave it alone entirely.
- **A detail is no longer overwritten by a request the user has moved on from.** Clicks and
  held-down arrow keys put several of them on the wire at once and they do not come back in order,
  so an older answer could land on top of the asset the user had already stepped to. Creating an
  asset opens the detail on it and takes its turn in the same order, so an answer from before that
  cannot land on it either.
- **Metadata for a selection that cannot be loaded no longer waits for ever.** The fetch was
  fire-and-forget, so a failure — or an asset that had since been deleted — left its items loading.
- **Two files of the same name no longer share a key in the queue.** Vue's keyed diff could patch
  the wrong tile, so removing one made another disappear.
- **The sign-in button shows that it is working**, and a second submit no longer starts a second
  request. A successful sign-in now reloads the page instead of routing to it: signing in as
  somebody else kept the first user's identity, permissions and configuration until the tab was
  reloaded by hand. Whatever the tab held is lost with the reload, which is the point of it.
- **Selecting exactly the maximum no longer warns that the limit was reached**, in the asset list
  and the external provider list. Importing exactly the maximum is now allowed as well — it used to
  be refused outright, with a warning of its own about the upload limit.
- **The file size limit is applied the right way round** for the `*` and `.extension` forms of the
  limit map, which accepted files above the limit and refused the ones below it. Nothing in this
  application passes those forms today — that half of the fix is for the next thing that does. The
  half that does apply is the boundary: the mime forms, which are the ones this application uses,
  refused a file whose size is exactly the limit, and the backend accepts it — `AbstractAssetFileFacade`
  asks `size <= sizeLimit`. Every form of the key now takes it. An `.extension` key is now matched against the file name as well, which it
  never was. The two checks moved out of the component into `fileValidation.ts`, which needs no
  Vuetify to test.
- **An upload that finishes without its metadata says so.** The metadata notification comes once,
  and a failed or lost one left the form disabled and the bulk save skipping that item in silence.
  A read that fails now says so on the row — a notification that never comes says nothing, but the
  row is offered the refresh button after twenty seconds at the latest — and that warning survives the
  file finishing — every other one is
  cleared there, including the fallback's own “this is taking too long”, which the user has just
  acted on. The refresh button stays for such an item, a duplicate excepted, which is not given
  metadata to edit at all, and refresh fetches the missing metadata rather than only the file
  status, clearing the warning when it arrives. A row that already has its metadata is left alone by
  a later failed read of the same asset.
- **A failed detail fetch no longer leaves a spinner.** Opening, refreshing or stepping to the next
  asset had no error handling at all, and the five-second detail cache was held even by a request
  that failed — which could open the fullscreen dialog on an asset that was never loaded, showing
  nothing at all and offering no way out but Esc. Only the newest of these requests may answer:
  they are counted in the detail store itself, so that the list, the queue dialog and the arrow
  keys share one count, and an answer that arrives after the user has moved on neither writes to
  the detail nor takes the spinner down under the request that replaced it. Closing the dialog is
  not moving on: the panel on the right renders whatever asset the store holds, so the newest
  request has to be left to write it — and when that request fails, the detail is cleared rather
  than merely closed, or the panel is left offering to save the asset before it.
- **The slot panel recovers from a failed load**, and making a file public or private for an asset
  type without a matching branch now fails instead of leaving the dialog loading for ever.
- **The library's upload status fallback follows its configuration** rather than being switched on
  regardless — this application's own fallback already did. The one exception is the
  external-provider import, which has no upload of its own whose finish would arm one: its item
  carries no ids until the import responds, and the notification can arrive before that response, so
  an import that loses that race would otherwise process for ever wherever the setting is off.
