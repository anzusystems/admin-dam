planned
===

### Fixed

- **Cancelling an upload now stops it.** The cancel token only existed while a chunk was in flight,
  so a stop asked for between two chunks, or during a retry back-off, was ignored and the file
  uploaded to the end anyway. The chunk loop now checks at every point it can be interrupted.
- **Removing an item from the queue while it uploads no longer reports a failure that did not
  happen.** The asset is deleted server-side first, so the loop went on posting chunks to something
  that was gone and ended on an error message about an upload the user had cancelled. The removal
  now tears the upload down the same way stopping it does, and refills the slot it freed — until
  now the queue stalled instead.
- **The upload queue keeps to its two parallel uploads.** It started two more whenever a slot came
  free, without counting the ones already running, so the number crept up under a long queue.
- **A stopped or cleared upload no longer leaves its notification fallback timer behind.** The timer
  reschedules itself, so an item removed while it waited went on polling for the asset for minutes.
- **Reporting an error no longer signs the user out.** The log request went through the
  authenticated client, and because the log endpoint is an absolute url the interceptor's `runWhen`
  filter did not exclude it: a 401 on a log request logged the user out. The log now goes through a
  client of its own, and a rejected log request is no longer an unhandled rejection.
- **The client no longer collects an interceptor per request.** `damClient()` is a factory called on
  every request — chunked uploads call it once per chunk — and it registered its request and
  response interceptors on the shared instance each time, so the handler arrays grew without bound
  for as long as the tab was open. The two arguments it accepted, `timeoutBase` and
  `onUploadProgress`, could never work on a shared instance either; chunk uploads now pass their
  longer timeout in the request config.
- **Notification listeners are registered once.** A repeated start-up added another listener and
  opened another connection, and nothing tore either down.
- **Reading the auth cookies no longer leaves a listener behind.** Both readers run outside a Vue
  effect scope, where VueUse's `useCookies()` leaks a `Cookies` instance and a permanent change
  listener per call and its own cleanup is a silent no-op.
